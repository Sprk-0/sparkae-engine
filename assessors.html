Objections Answered
Everything you're about to ask.

"Does this compromise our independence?"

The opposite. SparkAE is a third-party tool — not built by the CSP, not built by you. Using an independent validation engine is more defensible than homegrown tooling. When the PMO questions a finding, "the Examine method was run by an independent engine, and here is the evidence trace" is a stronger answer than "our assessor read it." SparkAE is not the assessor of record.

"What about CUI? Our clients' SSPs are sensitive."

The default self-contained mode (LLM_PROVIDER=none) makes zero external calls — zero outbound HTTP, zero DNS lookups, zero CDN. Docker container with read-only filesystem, cap_drop ALL, non-root. No API keys needed. A local LLM via Ollama keeps the same posture. Whether a given deployment is suitable for CUI depends on how you deploy and accredit it — the software supports the boundary, it does not confer the authorization.

"AI can't replace assessor judgment."

It doesn't try to. SparkAE automates the EXAMINE method only — document review against DIFs. INTERVIEW and TEST still require your assessors. Professional judgment still drives the final SAR. The tool removes reading. Not thinking.

"We'll just build our own."

You could. Then you'll pull two engineers off billable work for 6 months. Then NIST releases an update and you spend 3 weeks patching. Then a client asks for CMMC. Then OSCAL format changes. We maintain the Rev5 Examine engine. You stay accredited.

"How do we explain this to the PMO?"

SparkAE produces deterministic, reproducible findings. Same SSP + same rules = same output every time. The engine is auditable. The rules are transparent. The PMO wants consistency — that's exactly what a deterministic engine delivers.

"What if the CSP also uses SparkAE?"

That's the best case. If the CSP self-assesses with SparkAE before you arrive, you can see exactly what they found, what they remediated, and what's still open. That handoff saves your team weeks. Same findings format, same terminology, zero translation.

Market Reality
The OSCAL mandate is rolling out.

FedRAMP is moving authorization packages toward machine-readable form. RFC-0024, which first proposed the mandate, was closed — its requirements were modified and folded into the 2026 Consolidated Rules rather than adopted as drafted, so the specifics are still settling. What does not change is the direction: a Word/Excel-only workflow does not produce structured authorization data, and retrofitting it later is the expensive path. SparkAE exports native OSCAL 1.1.2 assessment-results and POA&M today.

FedRAMP 20x support is in development. What ships today is the Rev5 Examine engine, and the firms that adopt it still own the assessment.
